Visión general

Flujo de ejecución

Qué ocurre, en orden, cuando se llama a TemplateService.generate(template, values): tres etapas (parser, renderer, compiler) y en qué punto puede fallar cada una.

Secuencia de generate

Paso a paso

1. Parse: descubrir los campos

generate empieza llamando a self.parse(template), que delega en parse_template parser.py:20. Recorre la plantilla con MARKER_PATTERN.finditer y, por cada marcador:

  1. Lee el nombre, si lleva ? (opcional), el tipo (por defecto string, pasado a minúsculas) y el argumento entre paréntesis.
  2. Si el tipo no está en VALID_TYPES, lanza ParseError.
  3. Construye el TemplateField con _build_field: un enum sin opciones pasa a ser string, y un date guarda su argumento como formato.
  4. Si el nombre ya apareció, compara el campo nuevo con el guardado (igualdad de dataclass). Si difiere en algo, lanza ParseError; si es igual, lo ignora.

Resultado: un campo por nombre, en orden de primera aparición. Como generate analiza de nuevo, los campos que el cliente creyera tener no importan.

2. Render: validar, escapar y sustituir

Renderer.render(template, fields, values) renderer.py:24 hace tres cosas, en este orden:

  1. Obligatorios: junta todos los campos obligatorios sin valor y, si hay alguno, lanza un único MissingFieldsError con la lista completa. "Sin valor" significa None, ausente del diccionario o una cadena vacía o de solo espacios; 0 y False sí cuentan como valor renderer.py:101.
  2. Escape: para cada campo con valor pide su escaper a get_escaper y lo aplica. Un campo opcional vacío se convierte en "". Si el escaper lanza ValueError, se envuelve en InvalidFieldValueError con el nombre del campo. Se detiene en el primer valor inválido.
  3. Sustitución: MARKER_PATTERN.sub reemplaza cada marcador por el texto escapado de su campo. Todas las apariciones de un campo reciben el mismo valor. Un marcador cuyo nombre no está entre los campos se deja tal cual.

Los valores extra en values que no corresponden a ningún campo se ignoran.

3. Compile: LaTeX a PDF

TectonicCompiler.compile(tex_source) compiler.py:63:

  1. Crea un directorio temporal (se borra al terminar) y escribe ahí document.tex en UTF-8.
  2. Ejecuta tectonic --outdir <dir> <dir>/document.tex con subprocess.run, capturando la salida como texto y con un límite de timeout segundos (30 por defecto).
  3. Interpreta el resultado:
SituaciónResultado
No se encuentra el ejecutable (FileNotFoundError)Lanza CompilerNotFoundError.
Se agota el tiempo (TimeoutExpired)CompileResult(ok=False, errors=["Compilation timed out after 30s."]), con log vacío.
Código de salida distinto de 0CompileResult(ok=False, log=stderr, errors=…). Los errores son las líneas de stderr que empiezan por error: o por !; si no hay ninguna, ["LaTeX compilation failed."].
Código 0CompileResult(ok=True, pdf=<bytes de document.pdf>, log=stderr).

Solo se guarda stderr en log; stdout se captura pero no se usa.

4. Resultado

De vuelta en generate service.py:70: si result.ok es falso, lanza CompileError(result.errors, result.log); si no, devuelve result.pdf. Las excepciones del parser, del renderer y CompilerNotFoundError no se capturan: llegan a quien llamó tal cual.

Demostración interactiva

Escribe una plantilla y valores: la demostración ejecuta en tu navegador el parser y el renderer, con los mismos mensajes de error. No compila: el resultado es el LaTeX que recibiría Tectonic.

Port en JavaScript del core (docs/guide/demo.js), comparado con el Python real en 24 casos con resultados idénticos. Diferencias conocidas: en date solo acepta entradas AAAA-MM-DD y las directivas %Y %m %d %y %j %% (Python acepta más formas ISO 8601 y todas las directivas de strftime); en number solo dígitos ASCII.
